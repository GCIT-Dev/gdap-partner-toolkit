# Rewritten KB scripts

Between 2017 and 2020 GCIT published PowerShell scripts for managing many Microsoft 365 customers at once. They used DAP, the MSOnline and AzureAD modules, Azure AD Graph, basic authentication to Exchange Online, Azure Functions v1 and stored admin passwords. All of those are retired or unsafe, so the original scripts no longer run (or should not be run).

This folder holds working replacements built on the MspGdap module and GDAP. There are 69 scripts covering 74 of the 83 original articles. The other 9 articles are listed at the end with the reason they have no script: 8 cover a retired product or feature, and 1 still works as published.

[`MAPPING.json`](MAPPING.json) is the machine-readable version of the tables below: one entry per original article with its status, the method it replaced, the script (or null), notes and any permissions the full manifest does not cover (none in this release).

## What every script has in common

- **No passwords or secrets.** Graph calls go through `Invoke-MspGraphRequest`, Exchange through `Connect-MspExchangeOnline` and Security and Compliance through `Connect-MspSecurityCompliance`, all with the technician's own GDAP token. Third-party API keys (IT Glue, UniFi, Have I Been Pwned) are read from a SecretManagement vault at run time.
- **One customer or all of them.** `-TenantId` takes one or more tenant IDs or verified domains, also from the pipeline. `-AllCustomers` runs against every customer from `Get-MspCustomer`, and skips customers without an active GDAP relationship. The three IT Glue and UniFi sync scripts work in your partner tenant only, so they have no `-TenantId`.
- **One row per result.** Output is `[pscustomobject]` rows that start with `CustomerTenantId` and `CustomerName`. `-OutputPath` also writes them to a CSV file.
- **A failed customer doesn't stop the run.** Each customer runs in its own `try`/`catch`, and failures come back as rows with a `Failed` status and the error.
- **Report only by default.** Where the original made changes, the rewrite only reports until you add `-Apply`. Every change goes through `ShouldProcess`, so `-Apply -WhatIf` previews it and `-Confirm` asks first.
- **Unsafe originals are not copied.** Scripts that created Global Administrator or Exchange admin accounts with a shared password, or added IP addresses to the MFA trusted IPs list, are replaced with the safe equivalent using the technician's GDAP role or app-only Exchange access.
- **Help on every script.** `Get-Help ./scripts/<folder>/<script>.ps1 -Full` shows the parameters, two examples, the GDAP roles and the exact partner app permissions it needs, and links to the original article.

## Prerequisites

1. PowerShell 7.4 or later (7.6 recommended) and the MspGdap module from this repository. See [01 Prerequisites](../docs/01-prerequisites.md).
2. The partner app created in your partner tenant. Most scripts need the [full manifest](../manifests/partner-app.full.json), because the minimal one leaves out permissions such as `Policy.ReadWrite.ConditionalAccess`, `Sites.FullControl.All` and `Mail.ReadWrite`. See [02 Create the partner app](../docs/02-create-partner-app.md).
3. A registered technician token. See [03 Register a technician token](../docs/03-register-technician-token.md).
4. The partner app pre-consented in each customer, with the same manifest. See [04 Pre-consent customers](../docs/04-preconsent-customers.md).
5. For Exchange and Security and Compliance scripts, `ExchangeOnlineManagement` 3.x and the right GDAP role. See [05 Exchange access](../docs/05-exchange-access.md).
6. A GDAP role in each customer that covers the script. Each script's help lists the least-privileged roles, and the table below repeats the main one.

Background reading: [06 Token caching and validation](../docs/06-token-caching-and-validation.md), [07 Migrating from DAP and MSOnline](../docs/07-migrating-from-dap-msonline.md) and, for the Azure Functions folders, [08 Unattended automation](../docs/08-unattended-automation.md).

## How to run a script

```powershell
Import-Module ./src/MspGdap/MspGdap.psd1
Set-MspConfiguration -PartnerTenantId '<PartnerTenantId>' -AppId '<PartnerAppId>' -CertificateThumbprint '<Thumbprint>' -VaultName 'MspGdap'

# Read the help first: roles, permissions and examples
Get-Help ./scripts/delegated-reporting/disable-pop-imap.ps1 -Full

# Report on one customer
./scripts/delegated-reporting/disable-pop-imap.ps1 -TenantId 'contoso.onmicrosoft.com'

# Report on every customer and save a CSV
./scripts/delegated-reporting/disable-pop-imap.ps1 -AllCustomers -OutputPath ./pop-imap.csv

# Preview the change, then make it
./scripts/delegated-reporting/disable-pop-imap.ps1 -TenantId 'contoso.onmicrosoft.com' -Apply -WhatIf
./scripts/delegated-reporting/disable-pop-imap.ps1 -TenantId 'contoso.onmicrosoft.com' -Apply

Disconnect-Msp
```

Try every script against one low-risk customer before you use `-AllCustomers`, and always run `-Apply -WhatIf` before `-Apply`.

### Azure Functions

Articles that ran on Azure Functions v1 have a `functions` folder next to their scripts ([automation/functions](automation/functions/), [security-and-graph-apps/functions](security-and-graph-apps/functions/)). Each function is a thin `run.ps1` timer trigger that calls the script from the same folder. They target Azure Functions v4 on PowerShell 7.6, use a managed identity to read the partner app certificate and refresh token from Key Vault, and only report unless the `MSPGDAP_APPLY_CHANGES` app setting is `true`. The publish layout and app settings are in each `profile.ps1`. Read [08 Unattended automation](../docs/08-unattended-automation.md) before you deploy one, and prefer app-only access where Microsoft supports it.

## Permissions

Every delegated permission these scripts need is in the [full manifest](../manifests/partner-app.full.json). Earlier copies of the manifest left out Microsoft Graph `Domain.ReadWrite.All`, `ServiceMessage.Read.All`, `IdentityRiskEvent.Read.All` and `IdentityRiskyUser.Read.All`. If your partner app was created from one of those copies, add the permissions to the app and consent again in each customer (`Grant-MspPartnerAppConsent -Force`). Until then the affected step fails with 403 and the customer is recorded as `Failed`.

No script needs Microsoft Graph `User.DeleteRestore.All`, and neither manifest includes it. [remove-deleted-user.ps1](users-and-licensing/remove-deleted-user.ps1) only lists deleted users. Permanently deleting a user cannot be undone and is rarely needed, so the toolkit leaves it as a manual step in the Microsoft Entra admin center rather than holding a standing permission for it. If your partner app was created from a 0.2.1 pre-release copy of the full manifest that included it, remove it from the app.

`tests/Scripts.Tests.ps1` checks every script here: it parses, requires MspGdap and PowerShell 7.4, has full help with links, exposes `-TenantId` (or explains why not), uses `ShouldProcess` for every change and contains none of the retired methods (MSOnline, AzureAD, AzureRM, Azure AD Graph, basic authentication remote PowerShell, password grants, AES key files). It also checks that `MAPPING.json` and this file agree with the scripts on disk. The `tests/scripts` folder runs each script with mocked Graph and Exchange calls against `contoso.onmicrosoft.com`, including `-WhatIf` runs that must not write anything. No test contacts a real tenant.
